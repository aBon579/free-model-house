## 1. 指纹诊断器（`/api/diagnostics`）

### 做了什么

上游改了规格时，闸门只给一句 `403 FreeTierError`。
根因有 **6 种可能**（端点 / UA / 会话头 / 会话 ID / 工具定义 / tool_choice），
错误体**一个都不告诉你**。

人工排查要 **6 轮往返**（改一处 → 重启 → 等上游 → 试一次）。

FMH 把**单变量对照**做成了自动的：
从一份"已知能通过"的请求出发，**每次只改一项**，看它是不是被拒。

### 实测（真实上游）

```
基线通过: True (HTTP 200)  耗时 8.0s
结论: 上游在管的是：**User-Agent**
  端点路径            通过
  User-Agent         被拒 426  OpenCode 1.18.0 or newer is required to use the free
  会话头 / 会话 ID / 工具定义 / tool_choice   通过
```

⚠️ **状态码是 426（Upgrade Required），不是 403**。
但两者都归 `FREE_TIER_BLOCKED`。

### 踩到的坑

**坑 1：诊断请求必须跟生产同款。**

第一版诊断基线就 403。原因是手写了请求头，漏了
`x-opencode-client` 和 `x-opencode-project`，
而且用了 `stream: false`（生产一直用流式）。

修法：**直接用 `ZenHeaders` + `ZenApplyFingerprint`**，
不要重造一遍。

**坑 2：变体必须在注入之后施加。**

`ZenApplyFingerprint` 会把 `tool_choice: "none"` **删掉**
（闸门见 `none` 就 403）。
先改后注入 = 变体被撤销 = 测出来永远是"通过"。

**坑 3：限流被误判成"上游改了规格"。**

浏览器测试时点完「立即检查」紧接着点「开始诊断」，
吃到 429，诊断器报"基线就被拒 —— 上游改的不是一处"。

这是**误导性结论** —— 用户会去改指纹文件，而那**完全没有用**。

修法：基线失败要**分类**：

| 基线的失败 | 结论 |
|---|---|
| 429 限流 | "上游在挤，不是在拒绝我们，等几分钟再试" |
| 传输层错误 | "网络问题或出口被封，不是规格问题" |
| EGRESS_BLOCKED | "出口 IP 被风控，换出口" |
| 403 / 426 | "真的被拒" —— 只有这种才继续往下测 |

⚠️ 这个坑是**测试时自己撞上的** ——
   如果只跑单元测试（假上游固定返回 200），根本发现不了。

### 测试

| 测试 | 覆盖 |
|---|---|
| `TestDiagnosePointsAtBrokenDimension` | 6 个维度**逐个**改坏，都能**准确定位** |
| `TestDiagnoseBaselineFailureIsReported` | 基线不通时**不**给逐项结果 |
| `TestDiagnoseThrottleIsNotGateRejection` | 429 **不能**说成"上游改了规格" |
| `TestDiagnoseTransportErrorIsNotGateRejection` | 连不上**不能**说成规格问题 |
| `TestDiagnoseAllHealthy` | 全通过时给出正确结论 |

## 2. 探测批量自适应

### 做了什么

免密车道的配额是**全局共享**的。
高峰期继续按正常节奏探测 = **拿额度去撞限流墙**：
探到的全是 429，既费额度又拿不到有效信息。

批量跟着**上一轮的限流比例**走：

| 上一轮限流比例 | 本轮批量 |
|---|---|
| 0% | 100% |
| 25% | 75% |
| 50% | 50% |
| 75%+ | 25% |

### 为什么用"上一轮"而不是"这一轮"

因为要算批量就得看限流情况，
而限流情况要等**探完**才知道。
用上一轮的数据 = 天然的一轮延迟，而且预测效果够好。

⚠️ 而且这样**不用在锁里查 catalog** ——
   `PickTargets` 可能已经持有 catalog 的锁，
   在调度器的锁里再查就是**死锁**。

### 测试

`TestAdaptiveBatchShrinksWhenThrottled`（限流 100% → 批量降到 1/4）、
`TestAdaptiveBatchGrowsWhenHealthy`（恢复后调回满）、
`TestAdaptiveBatchCanBeDisabled`、
`TestAdaptiveBatchNeverZero`（不能探 0 个）。

## 3. 费用透出

### 做了什么

只有 OpenRouter 报 `usage.cost`。但**必须透出** ——
用户可能把 OpenRouter 当主力，而"悄悄扣钱"是**最坏的体验**。

### ⚠️ 关键：列类型必须是 `REAL`

`INTEGER` 会把 `$0.0000043` 截成 `0`，
看起来像"完全没花钱"，而额度在**悄悄消耗**。

### ⚠️ 关键：加列要处理"列已存在"

`CREATE TABLE IF NOT EXISTS` **不会**给已存在的表加新列，
所以老数据库必须显式 `ALTER TABLE ADD COLUMN`。
而加列**不幂等** —— 重复加报 `duplicate column name: cost_usd`，
必须**当成功**处理。

⚠️ 错误措辞在不同 SQLite 版本不一样
（`duplicate column name` vs `column already exists`），两种都要匹配。

### ⚠️ 关键：费用是"设置"不是"累加"

OpenRouter 的最后一帧带完整 usage。
如果中间帧也带 cost，累加就会**翻倍** ——
那是"报告了双倍花费"，比不报更糟。

### 测试

`TestMigrateAddsCostColumn`（幂等 + 小额不截断）、
`TestCostAccumulatesAcrossDays`、
`TestDecodeCostUSD`、`TestDecodeCostMissingIsZero`、
`TestDecodeCostIsSetNotAccumulated`。

## 4. 移动端触屏适配

### ⚠️ 先澄清一个误解

**移动端**不是**另一个网页**。

同一个 URL、同一份 bundle、同一个 `index.html`。
差别只在**布局怎么排**，全靠 CSS 媒体查询。

- **没有** `navigator.userAgent` 判断
- **没有** `/m` 之类的移动端路由
- **没有**两套构建产物

### 做了什么

**① 触点尺寸。**

桌面端 28px 的小按钮是**故意**的（表格紧凑）。
但手机上点不准（Apple 建议 44px）。

用 `@media (pointer: coarse)` 区分触屏：

```css
.fmh-touchable      { min-height: 36px; }
.fmh-touchable-icon { min-width: 40px; min-height: 40px; }
```

**② 开关的热区。**

开关视觉只有 22px 高，但**可点区域**要够。
用伪元素撑开，**视觉完全不变**：

```css
.fmh-switch::before { content: ''; position: absolute; inset: -9px -1px; }
```

**③ 安全区。**

刘海屏 / 底部横条：

```css
--safe-top: env(safe-area-inset-top, 0px);
--safe-bottom: env(safe-area-inset-bottom, 0px);
```

三个应用点：顶栏、侧栏、内容区。

### 实测（375px，`isMobile + hasTouch`）

| 检查 | 结果 |
|---|---|
| 页面主体按钮 | 全部 ≥ 36px ✅ |
| 抽屉导航项 | 220×36 ✅ |
| 开关热区 | 视觉 38×22，偏 8px 点击**仍命中** ✅ |
| 横向溢出（5 页 × 3 视口） | 全部 0px ✅ |
| 控制台错误 | 0 ✅ |

### ⚠️ 测的时候踩到的坑

**坑 1：`getBoundingClientRect()` 看不到伪元素。**

开关加了 `::before` 之后，视觉盒子还是 22px，
测出来"还是偏小"。

必须用 `document.elementFromPoint()` 测**热区**，
而不是量**盒子**。

**坑 2：Go 二进制要重新编译。**

前端 CSS 是 `go:embed` 进二进制的。
只跑 `npm run build` 不重新 `go build`，
服务里跑的还是**旧 CSS**。

⚠️ 这个坑让第一轮修复"看起来没生效"，
   白测了一遍。
