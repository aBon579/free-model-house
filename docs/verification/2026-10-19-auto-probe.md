> ⚠️ **术语说明**：本文记录的是 **2026-10-19** 那次排查，

## 1. 为什么"自动探测"不是一个定时器那么简单

**每次探测 = 一次真实推理。**

28 个模型全探一遍 = 28 次推理。每 10 分钟一次，一天就是
`28 × 144 = 4032 次`推理。

而且限流本身会让探测变得**更贵** —— 被限流的模型重探也是浪费。

所以"每 N 分钟全量轮询"是**错误**的设计。FMH 的调度策略是
**按需探测**：

| 规则 | 理由 |
|---|---|
| ① **只探免费的** | 探测付费模型**可能**真扣钱。虽然实测它在凭据检查阶段就 401 了（不花钱），但那只是运气好，不能依赖 |
| ② **只探过期的** | 结论有 10 分钟 TTL。新鲜的不重复探 —— 重复探 = 重复花钱 |
| ③ **每轮只探 N 个** | 默认 4 个。少量多次比一次全量更划算，也更不容易撞上配额墙 |
| ④ **轮转覆盖** | 用游标轮转，保证每个模型最终都会被探到。否则排序靠前的永远被探，后面的永远"未知" |
| ⑤ **并发上限** | 同时最多 2 个。免密车道的配额是全局共享的 |
| ⑥ **失败退避** | 连续失败的模型**等几轮**再探。一直报错的模型每轮都探就是纯浪费 |
| ⑦ **连续失败 5 次就不再探** | 5 次连续失败多半是**上游收紧了**，继续探只是烧配额 |

## 3. 两个 API

### 3.1 单模型探测（同步）

```
POST /api/probes/run  {"model": "minimax-m3.1-flash-free"}
```

用户点了按钮就该等结果（通常 1–2 秒）。

### 3.2 整轮探测（异步）

```
POST /api/probes/run  {}
→ 202 {"ok": true, "async": true, "note": "探测已在后台启动 —— 这会消耗上游额度"}
```

全量探测要几十秒，不能让 HTTP 请求挂在那儿。

> ⚠️ **这里踩了一个坑**：
>
> ```go
> go a.prober.RunOnce(r.Context())   // ❌
> ```
>
> `r.Context()` 在**响应写完时就被取消** ——
> 探测 goroutine 会立刻死掉，一个模型都探不到。
> 而且它**不报错**（就是静默地什么都不做）。
>
> 正确写法：
>
> ```go
> go a.prober.RunOnce(context.WithoutCancel(r.Context()))   // ✅
> ```
>
> `WithoutCancel` 保留 context 的值（超时等），但**去掉取消信号**。

## 4. 实测（真实上游）

### 4.1 单模型探测

```
POST /api/probes/run {"model": "minimax-m3.1-flash-free"}
→ 200, 1.1s
  状态: available
  延迟: 1051 ms
  首字: 984 ms
```

### 4.2 整轮探测

```
POST /api/probes/run {}
→ 202 {"async": true}
（12 秒后）
summary: {"available": 1, "failed": 3, "unknown": 0, "probed": 4}
```

⚠️ **恰好探了 4 个** —— 就是配置的批量大小。

### 4.3 探测结论（真实上游，与 M1 手工测试的结论一致）

| 模型 | 状态 | 说明 |
|---|---|---|
| `minimax-m3.1-flash-free` | **available** | 1051ms |
| `deepseek-v4.1-flash-free` | **throttled** | `Rate limit exceeded. Please try again later.` |
| `big-pickle` | **throttled** | 同上 |
| `beam-free` | **region-blocked** | `This model is not available in your country` |

> 这与 M1 阶段手工探测的结论**完全一致** ——
> 说明调度器没有引入任何偏差。

### 4.4 落盘与恢复

```
probes 表:
  ('minimax-m3.1-flash-free', 'available', 1051, 984)
  ('beam-free', 'region-blocked', 246, 246)
  ...
```

重启后：
```
fmh 恢复探测结论 4 条
```

且**模型行上的状态也跟着恢复**（见 §6 的 bug 2）。

## 6. 接线过程中抓到的 3 个 bug

### Bug 1：异步探测用 `r.Context()` —— 静默不工作

**症状**：点「探测一轮」返回 202，但 12 秒后 `probed` 仍然是 0。

**原因**：见 §3.2。

⚠️ 这个 bug **特别难查** —— 它不报错，日志里也什么都没有。
是实测"12 秒后 summary 没变"才暴露的。

### Bug 2：清单刷新会**清掉**模型行上的探测状态

**症状**：重启后所有模型都显示"未知"，**尽管** `probes` 表里明明有 4 条结论。

**原因**（两层）：

1. `Catalog.Replace` 换掉整个 `models` 切片 —— 新行是"干净"的，
   `state` 和 `ttftMs` 都是空。`probes` map 保留了，但**没人把它套回新行**。

2. 恢复探测结论发生在**拉清单之前** —— 那时 catalog 里还没有模型行，
   `ApplyProbe` 找不到可写的对象。

**修法**：

- `Catalog.Replace` / `Merge` **自动**把已有结论套回模型行
  （`applyProbesLocked`）—— 不依赖调用方记得做
- 恢复路径改用 `SetProbe`（只记结论），
  由 `Replace` 在清单到位后统一套用

**教训**：这类"生命周期"问题应该在**数据结构层**解决，
而不是靠调用方的顺序纪律。

⚠️ 附带修了一个**前后端状态值不一致**的 bug：
后端用 `region-blocked`（连字符），前端类型写的是 `region_block`（下划线）——
于是 `region-blocked` 落进了 `unknown` 分支，用户看到的是"未知"而不是"区域限制"。

### Bug 3：探测结论**没有写回模型行**

**症状**：手动探测返回 200，但 `/api/models` 里模型的状态还是空的。

**原因**：`ApplyProbe` 由**调用方**（main 的 hook）调用 ——
一旦有人忘了调，结论就只停在 `probes` map 里。

**修法**：把 `ApplyProbe` 移到**调度器内部** ——
探测的结论**就该**体现在清单上，不该依赖调用方的记忆。

## 7. 顺带修的

| 项 | 说明 |
|---|---|
| **冷却倒计时接进 API** | `CooldownRemaining` / `RecoveryETA` 实现了但没人用。现在 `/api/models` 会返回 `cooldownSec` 和 `recoveryAt` |
| **探测结论的说明** | `/api/models` 现在返回 `probeDetail`（"为什么不可用"） |
| **探测统计** | `/api/probes` 现在返回 `summary`（可用/异常/未知/总数） |
| **探测间隔可配** | `probeIntervalMin` 之前也只写不读，现在真正生效 |
| **批量大小可配** | 新增 `probeBatchSize` 设置 |

## 8. 现在的不足

| 项 | 状态 |
|---|---|
| **断流续写没在真实截断上验证过** | ⚠️ 11 个单元测试覆盖逻辑，但没有真会截断的模型 |
| **OpenRouter 车道没跑过真实推理** | ⚠️ 缺 OR Key |
| **跨车道回落没端到端验证** | ⚠️ 需要"免密被 IP 封 + OR 有 Key" |
| **移动端 UI 没在真机验过** | ⚠️ 断点写了 |
| **没有并发压测** | ⚠️ 没测过 50 并发 |
| **没在 arm64 上实际构建过** | ⚠️ Synology/群晖常见 |
| **上游变更无自动检测** | ⚠️ 有 16 条回归清单但不定时跑 |
| **探测间隔调整后不立即生效** | ⚠️ 调度器的 ticker 在启动时定下；改设置要重启才生效。⚠️ 这是已知的粗糙处 |
