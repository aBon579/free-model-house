## 一、严重：思考内容会破坏延迟提交

### 症状

模型一旦开始输出 reasoning，响应立刻提交 `200`。
上游随后的 429 只能变成流内错误事件 ——
**客户端拿不到真正的 HTTP 429 与 `Retry-After`**。

### 原因

网关的提交判断是对的：

```go
if !committed && (c.Kind == lane.ChunkTextDelta || c.Kind == lane.ChunkToolCallDelta) {
    committed = true
    writer.commit()
}
```

但**执行顺序错了**：

```go
if err := encoder.Write(c); err != nil { return }   // ← 先写
```

`encoder.Write(reasoning)` → `writeChatChunk` → `emit` → `WriteSSE`
→ **立即 `WriteHeader(200)`**。

所以思考内容抢先提交了响应。

### 为什么这很严重

「延迟提交」是这套设计里反复强调的机制
（`docs/design/00-overview.md` §4.4、`03-api-surface.md`）。

它的全部价值在于：**上游的 429 + `Retry-After` 能作为真正的 HTTP 429 返回**，
因为客户端的退避逻辑靠它。

而"想了一分钟然后撞上配额墙"恰恰是**最常见的失败形态** ——
思考模型先输出一大段 reasoning，然后上游才拒绝。

换句话说：**这个 bug 让延迟提交在最需要它的场景里完全失效。**

### 修法

思考内容在提交前**缓冲**，等第一个答案承载的 delta 到达时
**先倒出缓冲再写正文**（顺序不变，只是不提前提交）。

```go
if !committed && c.Kind == lane.ChunkReasonDelta {
    pending = append(pending, c)
    return
}
if !committed {
    committed = true
    writer.commit()
    for _, p := range pending { _ = encoder.Write(p) }   // 先倒思考
    pending = nil
}
_ = encoder.Write(c)
```

### 测试

- `TestReasoningDoesNotCommitResponse` —— 思考后失败 → 期望 **429 + Retry-After**，
  且**不该有 SSE 帧**。修复前拿到 200，修复后拿到 429。
- `TestReasoningIsDeliveredAfterBuffering` —— 缓冲**不能变成丢思考**：
  思考内容必须送达，且顺序在正文之前。

> ⚠️ 这个 bug 是**审计时主动构造场景**发现的，
> 不是被现有测试抓到的 —— 之前的测试用的假车道要么直接失败、
> 要么不输出思考。

## 二、配置改了不生效

### 症状

在管理台改设置 → 界面显示"已保存" → 但运行时行为不变，
**要重启才生效**。

### 原因

`Admin.SetConfigHook` 定义了，但 **`main.go` 从未调用**。
设置只写进数据库，没有任何东西把它读回运行时。

同理 `applySettings` 只在启动时调一次。

### 修法

在 `main.go` 里接上：

```go
admin.SetConfigHook(func() {
    applySettings(db, router, logger)
    gateway.SetLanEnabled(db.GetBool(store.SettingLanEnabled, true))
})
```

### 实测

```
--- 关掉局域网推理 ---
  LAN Key 调推理: 403  ✅
  本机 Key 调推理: 200  ✅
--- 重新打开（不用重启）---
  LAN Key 调推理: 200  ✅  ← 立即生效
```

## 三、"局域网推理"开关是个摆设

### 症状

管理台有「局域网推理」开关，关掉之后：
界面上 LAN 那一行变灰、提示"去服务设置开启"，
但**推理接口照样能用**。

### 原因

`SettingLanEnabled` 只在 `admin.go` 里被**读取显示**，
**从来没有在网关上被执行**。

也就是说这个开关是纯装饰 —— 用户以为关掉了，其实没关。
**在一个安全相关的开关上撒谎，是最不能接受的一类 bug。**

### 修法

网关加一个 `lanEnabled` 开关 + 锁：

```go
if !g.LanEnabled() && !g.keys.MatchLocal(presented) {
    writeOpenAIError(w, http.StatusForbidden, ...)
    return
}
```

语义明确：**关掉它 = 只允许本机使用**（管理台还要能推理）。

### 测试

`TestLanDisabledBlocksLanKey` —— LAN Key → 403，本机 Key → 200。

## 四、限流账本与探测结论不恢复

### 症状

重启后：
- 刚被限流的模型**立刻又被试一次** → 再被限流 → 白白浪费一轮候选
- 所有模型的探测结论变成"未知" → 候选链的排序失去依据

### 原因

`saveThrottle` 在跑（写），但启动时**没有读回来**。
`LoadThrottle` / `LoadProbes` 在 `store` 里定义了却没人调用。

限流窗口尤其重要：冷却是**基于时间**的，
重启后冷却应该继续，而不是从头开始。

### 修法

`main.go` 加 `restoreState()`，启动时恢复两者。

⚠️ 修的过程中还发现一个隐蔽的坑：
限流账本的 `Book` 实例必须**和路由共享同一个** ——
最初写成 `lane.NewBook()` 传进去，恢复的记录路由器根本看不到。

### 实测

```
注入 1 条限流 + 1 条探测 → 重启 →
  fmh 恢复限流账本 1 条
  fmh 恢复探测结论 1 条
```

## 六、审计后仍然存在的不足

以下是**审计没能解决**的，需要更多工作：

### 6.1 自动探测完全没接线

`Probe()` 方法写好了，`probeEnabled` 设置项也有了，
但**没有任何定时器调用它**。

- 后果：模型清单里的"状态"列永远是"未知"（除非手动触发）
- 需要：后台循环里加一个探测 ticker，按间隔探测**已知免费**的模型
- ⚠️ 探测要**限流** —— 28 个模型全探一遍是 28 次真实推理

### 6.2 断流续写没有真实触发过

11 个单元测试覆盖了逻辑（消息结构、裁剪重复、换种子、抑制工具、次数上限），
但**没有一个测试真的让上游截断**。

需要：一个会截断的模型，或者一个能模拟截断的替身上游 + 端到端测试。

### 6.3 OpenRouter 车道没跑过真实推理

- 清单拉取 ✅（18 个免费模型）
- 配额查询 ✅（`401 "User not found."` 证明端点要 Key）
- **推理 ❌** —— 没有 OR Key

需要：一把真实的 OR Key 跑一遍，验证：
- `reasoning: {effort}` 真的生效（它声称是真档位）
- `reasoning.enabled: false` 真的能关掉思考
- 429 的 `Retry-After` 语义

### 6.4 跨车道回落没端到端验证

逻辑有（`allowCrossLane`），但没跑过
"免密被 IP 风控封 + OR 有 Key"这个真实场景。

### 6.5 限流冷却倒计时没显示

UI 上没告诉用户"这个模型还有 7 秒才能用"。
`CooldownRemaining` 实现了但没接进 API。

### 6.6 没有并发压测

50 并发下的行为未知。流式场景下每个连接一个 goroutine，
理论上没问题，但没测过。

### 6.7 移动端 UI 没在真机验过

响应式断点写了（≥1024 常驻 / 768–1023 图标条 / <768 抽屉），
但没在真机或真机模拟器上看过。

### 6.8 上游变更的应对流程只有文档

`docs/design/01-zen-fingerprint.md` 写了"上游改了怎么办"，
但没有**自动检测**（比如定期跑一遍 16 条回归测试清单）。

### 6.9 没有多架构构建验证

Dockerfile 支持 `GOOS=linux`，
但**没在 arm64（Synology/群晖常见）上实际构建过**。

## 七、审计用过的手法

1. **导出方法调用扫描** —— 找出"定义了但没人调"的方法
2. **设置项反向查找** —— 每个 `Setting*` 常量都去 grep 谁读它、谁执行它
3. **构造对抗场景** —— 造一个"先思考后失败"的车道，
   验证延迟提交是否还成立
4. **端到端复测** —— 每次修复后重跑全部 30 项
