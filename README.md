## 1. 它是什么

**Free Model House (FMH)** 是一个自托管的网关程序。它做三件事：

```
你的 Agent ──[fmh-xxx]──▶ FMH ──[Bearer public]──▶ OpenCode Zen 免密车道（zen）
                        ├─[无需凭据]──────▶ Kilo 免 key 池（kilo）
                        └─[你自己的 OR Key]▶ OpenRouter 免费模型（openrouter）
```

- **对调用方**：一个 OpenAI / Anthropic 兼容的 API，一个固定前缀的 Key。
- **对上游**：一个"看起来像官方客户端"的请求，加上故障转移。
- **对运维者**：一个 Web 控制台，看得到"现在哪个模型能用、为什么上次是它应的"。

### 它解决的核心问题

免费模型不是"接上就能用"的：

| 障碍 | FMH 的处理 |
|---|---|
| 免费车道**限制客户端** —— 只认官方客户端的指纹 | 复现官方客户端的**线上行为**（不是它的代码） |
| 免费车道是**全局共享配额** —— 高峰期大面积限流 | 跨模型的**故障转移**（可开关） |
| 付费模型和免费模型**混在一个清单里** | 三级信任链过滤 + `401` 探针判定 |
| 上游流**会断** —— 客户端拿到残缺答案却不知道 | **断流续写** |
| 上游**偷偷改了规格** —— 只给一句 `403 FreeTierError` | **合规监视器**：定期探测 + 区分"改规格"与"限流" |
| 多个 Agent 各自配置**很麻烦** | 一把 Key + 一个 Base URL |

### 三条车道的区别（重要）

|  | zen | Kilo | OpenRouter |
|---|---|---|---|
| **全名** | OpenCode Zen | Kilo 免 key 池 | OpenRouter 免费模型 |
| **需要你的 Key？** | ❌ 不用（共享的 `Bearer public`） | ❌ 不用 | ✅ **要** |
| **额度** | 全网共享的，高峰期限流 | 上游提供，不花你的钱 | 你自己的账户额度 |
| **模型数** | 10 个 | 17 个 | 18 个免费模型 |
| **默认** | ✅ 开启 | ✅ 开启 | ❌ 不配 Key 就不参与路由 |
| **需要客户端指纹？** | ✅ 要（复现官方客户端行为） | ❌ 标准 OpenAI 兼容 | ❌ 标准 OpenAI 兼容 |
| **参与自动探测？** | ✅ | ✅ | ❌ **不参与**（会花你的额度） |
| **回落到它** | — | ✅ 自动（免密→免密，不花钱） | 要**手动开**（会花你的额度） |

**为什么要有三条？**

免密车道的可用性**跟着出口 IP 走** —— 被风控时是**整条车道**失效，
换模型救不了。多一条免密车道（Kilo）就是多一个出口无关的备胎。

> ⚠️ **OpenRouter 的"免费模型"只是特价档** —— 对你免费，但**必须绑定账户**
> （没有 Key 直接 `401 User not found.`）。
>
> **不配 OpenRouter 完全不影响使用** —— 两条免密车道自己就能工作。

## 2. 30 秒上手

### 部署（拉镜像，推荐）

```bash
mkdir fmh && cd fmh
curl -O https://raw.githubusercontent.com/aBon579/free-model-house/main/docker-compose.yml
docker compose up -d
```

不用装 Go / Node，也不用构建 —— Docker 会按你的架构（amd64 / arm64）
自动拉对应镜像。

### 自己构建

```bash
git clone https://github.com/aBon579/free-model-house && cd fmh
docker compose up -d --build
```

需要能拉 `node:22-alpine` 和 `golang:1.26-alpine` 两个基础镜像。

📖 完整步骤见 [`docs/operations/nas-deploy.md`](docs/operations/nas-deploy.md)。

### 拿到 Key

**启动日志里就是完整 Key**：

```
fmh  本机 Key fmh-EXAMPLEKEY0000000000000000000000000000
fmh  局域网 Key fmh-EXAMPLEKEY0000000000000000000000000000
```

复制一行就能用。也可以：

```bash
docker exec free-model-house /fmh key          # 本机 Key（登录管理台用）
docker exec free-model-house /fmh key lan      # 局域网 Key（给 LAN 里的 Agent 用）
```

或者打开 `http://<NAS-IP>:8678/`，用本机 Key 登录后到「服务设置」查看。

⚠️ 不想让明文 Key 进日志（会被收进日志系统、贴到工单）？
   设 `FMH_HIDE_KEYS=1` 就只打指纹。

### 接进 Claude Code

```bash
export ANTHROPIC_BASE_URL="http://<NAS-IP>:8678/v1"
export ANTHROPIC_AUTH_TOKEN="fmh-你的key"
```

⚠️ `ANTHROPIC_BASE_URL` 要**带 `/v1`** —— Claude Code 会拼 `/v1/messages`。

### 接进 OpenAI 兼容客户端

```json
{
  "baseURL": "http://<NAS-IP>:8678/v1",
  "apiKey": "fmh-你的key"
}
```

### 模型名

```
zen/minimax-m3.1-flash-free
openrouter/deepseek/deepseek-chat-v3-0324:free
```

也可以只写 `minimax-m3.1-flash-free` —— 网关会自动找到它所在的车道。

> 完整的 6 种工具配置片段在 Web 控制台的「快速接入」页，一键复制。
> 📖 各客户端的完整配置见 [`docs/operations/lan-access.md`](docs/operations/lan-access.md)。

### 3.1 统一事件总线

三个上游协议、三种下游协议，用**一套内部事件**连接：

```
block-start → text-delta → reasoning-delta → tool-call-delta → block-end → usage → finish
```

| 上游协议 | 下游协议 | 编码器 |
|---|---|---|
| OpenAI Chat | OpenAI Chat / Responses / Anthropic | `encoder_chat.go` |
| OpenAI Responses | 同上 | `encoder_responses.go` |
| Anthropic Messages | 同上 | `encoder_messages.go` |

一个上游可以服务三种客户端，一个客户端也能被三个上游服务。

### 3.2 车道抽象

```go
type Lane interface {
    ID() string
    ListModels(ctx) ([]ModelInfo, *Error)
    Do(ctx, *Turn, emit func(Chunk)) (*Usage, FinishReason, *Error)
    Probe(ctx, model) ProbeResult
    Ready() bool
    Status() LaneStatus
}
```

| 车道 | 凭据 | 指纹 | 特点 |
|---|---|---|---|
| `zen` | 共享的 `Bearer public` | ✅ 需要 | 全局共享配额，可能被限流；IP 被风控时**整条**失效 |
| `kilo` | 无需凭据 | ❌ 不需要 | 标准 OpenAI 兼容；出口无关，是 zen 的备胎 |
| `openrouter` | 用户自己的 Key | ❌ 不需要 | 额度绑账户，稳定些；不参与自动探测 |

**OpenRouter 车道不是可选的** —— 免密车道的 IP 信誉一旦被封，
**换模型救不了它**（闸门对所有模型一视同仁），只能换车道。

## 4. 核心机制

### 4.1 免密车道的四维指纹

上游只接受"看起来像官方客户端"的请求。FMH 复现**线上行为**，四个维度缺一不可：

| 维度 | 要求 |
|---|---|
| User-Agent | `opencode/latest/2.0.26/cli` —— 形状 `opencode/<channel>/<version>/<client>`，主版本 ≥ 2，**整串匹配** |
| 会话头 | 四个头**同值**：`x-opencode-session`、`x-opencode-session-id`、`x-session-affinity`、`x-session-id` |
| 会话 ID | `ses_` + 12 位 hex（**倒序**时间戳编码）+ 14 位 base62 |
| 工具声明 | 必须声明 `read` + `shell`（**名字**大小写精确；描述与 schema 不校验） |

**绝不能**发 `x-opencode-request`（v1 时代的头，会 403）。

所有字面量集中在**一个文件**（`internal/lane/zen_fingerprint.go`），并配断言它们没被改动的测试。

> ⚠️ `read` / `shell` 的描述字符串用 **OpenCode 官方客户端**原文 ——
> 用官方原文最稳 —— 万一上游以后开始比对，也不会炸。
> 这跟 `Content-Type: application/json` 是一个性质：**协议常量**。

### 4.2 两层闸门

实测发现，拒绝有两种，**同一个错误类型，不同的消息**：

| 层 | 消息 | 能否伪造 |
|---|---|---|
| 身份层 | `free tier can only be used from within OpenCode` | ✅ 能（复制指纹即可） |
| 出口 IP 信誉层 | `detected abusive traffic from this IP address` | ❌ **不能** |

这决定了故障转移的形状：
- 身份层失败 → 修指纹就行
- IP 层失败 → **只能换车道**（OpenRouter）

### 4.3 候选链与故障转移

三条铁律，每条对应一类真实事故：

**① 429 绝不重试同一模型** —— 配额按 session 记账，重试 = 再烧一次。
换模型是唯一诚实的杠杆。

**② 一旦吐过内容，绝不换模型** —— 换了会内容重复/拼接错乱。
⚠️ 但**思考不算**"吐过内容" —— "想了一分钟然后撞上配额墙"
恰恰是最值得故障转移的情形。

**③ 请求自身的错（4xx）绝不换** —— 重放同样的 body 会重现同样的拒绝。

还有一条针对**车道级**失败的：

**④ 闸门拒绝 / IP 风控 → 跳过同车道的其余候选** ——
闸门对所有模型一视同仁，同车道内换模型是白费功夫。

### 4.4 延迟提交

流式代理最容易犯的错：一上来就写 `200 OK`，然后上游才告诉你被限流。
这时你只能往流里塞错误事件，而客户端的退避逻辑**看不到 `429` 和 `Retry-After`**。

FMH 的做法：**把响应头延迟到第一个"答案承载"的 delta**。

```
上游 429 + Retry-After: 7
  → 还没提交 → 返回**真正的** HTTP 429 + Retry-After
  → 客户端按它自己的退避逻辑重试 ✅
```

一旦发出第一个字节，200 就已提交，失败只能以流内错误事件传递。

### 4.5 断流续写

上游的流不是可靠的。三种断法：

| 断法 | 现象 |
|---|---|
| 截断 | 有 usage，没 finish_reason，文本停在一句话中间 |
| 静默停止 | 连接还开着，但一个字节都不来 |
| 纯思考截断 | 只有 reasoning，一个字正文都没有 |

三种都会让客户端拿到**残缺**的答案，而且它**不知道**答案残缺（流正常关闭了）。

**续写的关键是怎么把"已说出去的话"喂回上游。**

朴素做法（把已输出文本当成新的 user 消息）有两个问题：
上游会**重新说一遍**（客户端看到重复），而且对话历史被污染。

FMH 用**工具调用协议**：

```
① 伪造一次工具调用 __fmh_continue(参数 = 已输出的完整文本)
② 伪造一个空工具结果
③ 上游看到"我刚才调用了这个工具，参数是这些"
   → 就知道"这些是我说过的" → 从那里继续
```

配套的两个细节：
- **裁掉重复** —— 上游可能重说，`stripPrefix` 只发新增的部分
- **换新种子** —— 否则命中缓存，把刚才截断的答案原样再吐一遍

⚠️ 这是整个设计里最精巧也最脆弱的一环。它依赖上游"理解工具调用里的文本就是我的输出"这个行为。
所以它**有降级路径**：续写失败就如实报错，不假装成功。最多续写 2 次。

### 4.6 免费判定：三级信任链

| 级别 | 来源 | 用途 |
|---|---|---|
| 1 | **实测**（探针） | 最高 —— 知道模型真的能不能用 |
| 2 | 上游清单声明 | 高 —— 厂商自己说的 |
| 3 | 第三方目录（models.dev） | 中 |
| 4 | 本地规则表 | 低 |

⚠️ **一个关键的反直觉点**：

> `401 "Missing API key"` 是判定"这个模型**不免费**"的决定性信号。
> `Bearer public` 只对免费车道有效。

所以**探测一个付费模型不花钱** —— 它在凭据检查阶段就被 401 拒了，没有 usage 字段。
探测一个免费模型才消耗一次最小推理。

### 4.7 自动探测：按需，不是轮询

**每次探测 = 一次真实推理。** 28 个模型全探一遍，每 10 分钟一次，
一天就是 4032 次推理 —— 对"免费"车道来说是浪费。

所以调度策略是**按需探测**：

| 规则 | 理由 |
|---|---|
| 只探**免费的** | 探测付费模型**可能**真扣钱（实测是 401 不花钱，但那是运气好，不能依赖） |
| 只探**过期的** | 结论有 10 分钟 TTL，重复探 = 重复花钱 |
| 每轮只探 **N 个** | 默认 4 个。少量多次比全量更划算 |
| **轮转**覆盖 | 用游标轮转，保证每个模型最终都被探到 |
| **并发上限** 2 | 免密车道的配额是全局共享的 |
| **失败退避** | 连续失败的模型等几轮再探 |
| 连续失败 **5 次**就不再探 | 多半是上游收紧了，继续探只是烧配额 |

探测结论会**落盘**，重启后恢复 —— 不用重新探一遍。

> ⚠️ 探测**不会**自动重试被限流的模型 ——
> 探了也是 429，纯浪费。

### 4.8 能力结论的"未知 ≠ 不支持"

模型清单里的"支持图片 / 支持思考"标记，如果搞错方向，代价很大：

- 猜"支持"但实际不支持 → 请求失败
- 猜"不支持"但实际支持 → **误杀能用的模型**，整个请求失败

所以 FMH 区分三种状态，UI 上分别画成**实心 / 删除线 / 虚线空白**：

| 状态 | 含义 | 硬过滤？ |
|---|---|---|
| 支持 | 实测或上游声明 | — |
| 不支持 | 实测或声明"不支持" | ✅ 是 |
| **未测量** | 规则表没匹配到 | ❌ **否** |

**"没测过"不能当"不能"用。** 只有"已知不行"才是硬约束。

### 4.9 限流冷却：10 秒

免费车道的凭据是**全局共享**的，所以 429 反映的是"此刻拥挤"，**不是**"这个模型坏了"。

实测 92 次限流事件里，**最短的一次只持续 0.6 秒**。

所以无 `Retry-After` 时的默认冷却是 **10 秒**，不是 60 秒。
冷却过长会让面板显示"不可用"而模型其实好好的 —— 候选链会跳过被限流的模型，用户看到的是一个**假的故障**。

### 4.10 自动跨模型调用：默认关闭，而且**必须**关闭

免密车道的失败分两类：

| 类别 | 例子 | 换模型有用吗？ |
|---|---|---|
| **模型级** | 限流、区域限制、模型不存在 | ✅ 有用 |
| **车道级** | 上游闸门拒绝、出口 IP 风控 | ❌ **完全没用** |

**关闭时（默认）**：

> 只重试**当前模型**。重试仍失败就**直接报错** ——
> **一个模型都不换**。

用户指名了哪个模型，就用哪个。模型不行就**明说不行**，
而不是悄悄换成一个他没要过的模型。

**开启时**：

| 顺序 | 切到哪里 | 花谁的钱 |
|---|---|---|
| ① | **Kilo ↔ Zen**（另一条免密车道） | 不花任何人的钱 |
| ② | 两条免密都无可用模型 → **OpenRouter** | **用户自己的额度** |

同车道内的**其他模型**也在候选里 —— 语义是**模型级别**的，
不只是换车道。

#### 账号级配额要**直接跳车道**

OpenCode Zen 的 `Free usage limit reached` 是**整个账号**的配额 ——
同一个车道的其他模型**一样**会被拒。

所以遇到这种错误会**跳过整条车道**，直接去另一条免密车道。

> ⚠️ **不处理的话会踩这个坑**：
> 候选链会把 6 次尝试（`maxFailover`）**全烧在同一条车道上** ——
> 结果就是"开着自动跨模型调用，却永远轮不到 Kilo"。
>
> 这是**实测踩到的**，不是理论推导。

⚠️ 但**模型级**配额（"这个模型没额度了"）**不跳车道** ——
那会让同车道的其他模型白白受牵连。判据看错误消息文本。

> ⚠️ **这里踩过一个严重的坑**：
>
> 守卫原本写在**尝试之后**，而且比的是"上一个失败候选的车道"。
> 结果是：开关**关了**，OpenRouter 候选**照样被调用**了 ——
> 用户的额度**已经被消耗**，而开关形同虚设。
>
> 正确写法是**尝试之前**判断，并且比的是
> "**这个候选**的车道" vs "**请求原本要的车道**"。
>
> ⚠️ 还有第二个坑：**关掉开关也拦不住免密车道之间互切**。
> 那时候候选链永远是整个模型池，开关只管"能不能用花用户额度的车道"。
> 现在候选链**在关闭时就被裁剪成只剩请求的模型** ——
> 开关才真的管得住。

### 4.11 上游合规监视器

免密车道的闸门**只给一句话**：`403 FreeTierError`。

也就是说上游**改了规格**时，症状是"所有模型同时不可用"，
而根因有 **6 种可能**（端点 / UA / 会话头 / 会话 ID / 工具定义 / tool_choice），
错误体**一个都不告诉你**。

更糟的是它**静悄悄地**坏 —— 没有告警、没有日志。

所以 FMH **定期用一个模型探一次**（30 分钟一次），并**分类**：

| 上游的反应 | 结论 |
|---|---|
| 200 | 上游正常 |
| 429 限流 | **上游正常**（只是限流）—— 限流**不是**规格问题 |
| 403 FreeTierError | **闸门拒绝** —— 规格变了，或出口被封 |
| 网络错误 | 探不到上游 —— 不是规格问题 |
| "模型不可用" | **换一个模型再试** —— 模型下架 ≠ 闸门坏了 |

「上游源」页顶部有明确的状态灯，闸门拒绝时还会给出**排查方向**
（改指纹文件 / 换出口 / 开自动跨模型调用）。

检查间隔**可配置**（默认 30 分钟，下限 5 分钟）—— 因为每次检查是一次真实推理。

---

### 4.12 指纹诊断器：**别猜，测出来**

上面 6 种可能，靠人工排查是 **6 轮往返**：
改一处 → 重启 → 等上游 → 试一次。每轮几分钟。

FMH 把这套**单变量对照**做成了自动的：

```
基线   ── 200 ──▶ 只坏了一项（或没坏）
     └─ 403 ──▶ 坏了多项，或坏了全局维度（端点/UA）

基线通过后，逐项"故意改坏"：
  改 UA     ── 403 ──▶ ⚠️ 上游在管 UA
  改端点   ── 200 ──▶ 上游不管端点
  …
```

**7 次请求**（1 基线 + 6 变体），一次给出结论。

实测（2026-10-19，真实上游）：

```
基线通过: True (HTTP 200)
结论: 上游在管的是：**User-Agent** —— 改这一项会被拒，其余随便改都通过。
  端点路径            通过
  User-Agent         被拒 426  OpenCode 1.18.0 or newer is required to use the free
  会话头 / 会话 ID / 工具定义 / tool_choice   通过
```

⚠️ **结论要如实读**：只有 UA 被管 **≠** 其它维度可以乱来。
上游随时可能加严，而且我们**无法预知**它会加严哪一条 ——
所以那 6 条规矩仍然全部照做。

⚠️ **基线不通时不能说"是第 X 项坏了"** —— 那说明坏了不止一处，
诊断器会如实报告"基线就被拒"，让人工去核对。

⚠️ 变体被拒时是 403/426，**不花钱**；基线通过时那 1 次是真实推理，**花钱**。
所以只在闸门拒绝时才跑。

详见 `docs/design/01-zen-fingerprint.md` §10。

---

### 4.13 探测批量自适应：**上游越拥挤，探得越少**

免密车道的配额是**全局共享**的。

高峰期上游在限流 —— 这时候继续按正常节奏探测，
就是**拿额度去撞限流墙**：探到的全是 429，既费额度又拿不到有效信息。

所以批量跟着拥挤程度走：

| 上一轮限流比例 | 本轮批量 |
|---|---|
| 0% | 100% |
| 25% | 75% |
| 50% | 50% |
| 75%+ | 25% |

可以关掉（设置页有开关）。

⚠️ 判据用的是**上一轮**的限流比例 ——
   上一刻的拥挤程度，对下一轮来说是很好的预测。
   而且这样**不用**在锁里查 catalog（会死锁）。

---

### 4.14 费用透出：**花了多少钱**

只有 OpenRouter 报 `usage.cost` —— 免密车道永远是 0。

但**必须透出**，因为用户可能把 OpenRouter 当主力，
而"悄悄扣钱"是**最坏的体验**。

- 存库：`cost_usd REAL`（⚠️ **不能是 INTEGER** —— 一次调用可能是 $0.0000043，
  按整数存会被截成 0，看起来像"完全没花钱"，而额度在**悄悄消耗**）
- 汇总：按天 + 按模型
- 界面：用量页显示总额和每模型花费；上游源页显示剩余额度 + 已用

⚠️ 小额要多给几位小数（`$0.0000043` 显示成 `$0.00` 是**误导**）。

## 5. 技术选型：为什么是单语言

### 5.1 结论

**后端 Go（单语言）。前端 TypeScript 是构建期边界，不是运行时边界。**

```
运行时：Go 一个进程，一份内存，一套并发模型
构建期：React/TS → 静态资源 → go:embed → 同一个二进制
```

### 5.2 为什么不是"多语言交叉编码"

你问过"单一语言还是多语言交叉编码"。我明确**拒绝**了交叉编码，理由：

| 交叉编码的典型形态 | 为什么不适合这个项目 |
|---|---|
| Go 后端 + Node 前端 + gRPC 桥 | 桥本身要部署、要版本匹配、要在 NAS 上多占一份内存 |
| Go + WASM（浏览器里跑 Go） | 体积暴涨，收益为零 |
| Go + C/Rust 扩展（FFI） | 需要 CGO → 破坏静态编译 → Docker 镜像做不进 scratch |
| Python 后端 | 依赖地狱；NAS 上 CPU 弱的机器上吞吐差；打包体积大 |

**这个项目的核心矛盾是"要在 NAS 上长期稳定跑"，不是"要榨干性能"。**
引入语言边界的代价（部署复杂度、内存占用、版本漂移）
远大于收益（开发时的语言偏好）。

### 5.3 Go 与其他候选的对比

| | Go | Rust | Python | Node |
|---|---|---|---|---|
| 静态编译 → scratch 镜像 | ✅ | ✅ | ❌ | ❌ |
| 无 CGO 的 SQLite | ✅ `modernc.org/sqlite` | ✅ | ✅ | ❌ |
| 并发模型适合大量流 | ✅ goroutine | ✅ tokio | ❌ GIL | ⚠️ 单线程事件循环 |
| 交叉编译到 NAS 架构 | ✅ 一行 | ✅ | ⚠️ | ⚠️ |
| 开发速度 | ✅ | ❌ | ✅✅ | ✅ |

⚠️ **关键约束：`CGO_ENABLED=0`。**
`mattn/go-sqlite3` 需要 CGO，会破坏静态编译 —— 所以用**纯 Go 的
`modernc.org/sqlite`**。这个选择是被 Docker 镜像目标倒逼出来的。

### 5.4 前端为什么是 TypeScript

- 界面逻辑是**声明式**的，TS 的类型能抓住 80% 的 UI bug
- 但它是**构建期**的：编译成静态资源，`go:embed` 进二进制
- 运行时**没有 Node、没有 npm、没有 dev server** —— NAS 上只有一个二进制文件

### 5.5 前端库的选择

**自己写组件，不引 shadcn/ui。** 理由：
shadcn 是 Radix + CVA 的重依赖，而且会带来自带的一套风格。
只用 4 个库：

| 库 | 用途 |
|---|---|
| `lucide-react` | 图标 |
| `@tanstack/react-query` | 数据缓存 / 失效刷新 |
| `@tanstack/react-virtual` | 虚拟滚动（50+ 模型要流畅） |
| `clsx` + `tailwind-merge` | class 合并 |

**不引入 Redux/Zustand** —— 全局状态只有两样（当前页面、主题），其余全是服务端状态。

## 6. 设计与实现

这一节说明 FMH 的**设计推导** —— 每个决定为什么这么做。

### 6.1 规格从哪来

免密车道的规格有两个来源，**都是第一手的**：

**① 上游客户端的公开源码**

OpenCode 的客户端是**开源**的（MIT）。免费车道既然只接受官方客户端，
那么"官方客户端发出去的请求长什么样"就是**公开可读**的：

```
https://github.com/sst/opencode
  packages/core/src/tool/plugin/read.ts     → read 工具定义
  packages/core/src/tool/plugin/shell.ts    → shell 工具定义
  packages/core/src/session/model-request.ts → 会话头
```

`model-request.ts` 里能直接读到的：

```ts
headers: {
  "x-opencode-session-id": session.id,
  "x-session-affinity":    affinity,
  "X-Session-Id":          affinity,
  "User-Agent":            App.useragent(app),
  "x-opencode-project":    session.projectID,
  "x-opencode-session":    affinity,
  "x-opencode-client":     app.name,
},
// 下一行的正则，直接给出了会话 ID 的形状：
promptCacheKey: /^ses_[0-9a-f]{64}$/.test(affinity) ? affinity.slice(4) : affinity,
```

FMH 的 `internal/lane/zen_fingerprint.go` 就是照着这些**协议事实**实现的。

**② FMH 自己的实测**

源码里读不出来的部分（上游的私有行为），靠实测确定：

| 实测结论 | 意义 |
|---|---|
| 端点按**模型名**分流（`muse-spark-*` 走 responses，其余走 chat） | 上游清单不声明 wire 信息 |
| 会话 ID 的 12 位 hex 是**降序时间戳** `~(ts_ms<<12\|counter)` | 形状对但编码不对也 403 |
| 闸门有**两层**：身份层 + IP 信誉层 | 两层的错误文案不同，要分开处理 |

**唯一的逐字照搬是工具描述**（`read` / `shell`）——
按 MIT 许可，上游的版权声明保留在 [`LICENSE`](LICENSE) 里。

> ⚠️ **实测（2026-10-22）的修正**：
> 之前这里写的是"上游**逐字比对**工具描述，改一个词就 403" ——
> **那是错的**。把两个工具的描述**全部乱写**，照样返回 200。
>
> 真正被校验的是：**UA 形状 · 四个会话头 · 会话 ID 形状 · 流式 · 有 read+shell 两个工具**。
> 工具描述**不在其中**。
>
> 用官方原文仍然保留 —— 官方客户端就长那样，
> 保留原文能保证"万一上游以后开始比对"时也不炸。
>
> 同样被推翻的还有"`tool_choice: "none"` 一律 403" ——
> 实测 200。FMH 里清除 `none` 的那段代码是**为了正确性**，
> 不是为了过闸门（`none` 会让模型这一轮不调工具）。

#### 闸门到底比什么（实测，2026-10-22）

直接构造请求打上游，一次只改一个变量：

| 测试 | 结果 |
|---|---|
| 完整请求（复刻 FMH） | ✅ 200 |
| `accept: application/json` | ✅ 200 |
| 不带 system 占位提示 | ✅ 200 |
| 去掉 `x-opencode-client` / `x-opencode-project` | ✅ 200 |
| **工具描述全部乱写** | ✅ 200 |
| **`tool_choice: "none"`** | ✅ 200 |
| **非流式**（`stream: false`） | ❌ 403 |
| **不带工具** | ❌ 403 |
| **去掉全部会话头** | ❌ 403 |
| **User-Agent 换成随意的** | ❌ 403 |

**必须全部满足**：UA 形状 · 四个会话头同值 · 会话 ID 形状 · 流式 · 有 read+shell。
**不看**：`accept`、`x-opencode-client`、`x-opencode-project`、system 提示、
**工具描述的任何字**、`tool_choice`。

> ⚠️ 之前这里写的是"上游按什么条件放行**尚未完全定位**" ——
> **现在定位清楚了**。
>
> 之所以之前测不出来，是因为**测试方法有问题**：
> 那些请求都是**通过 FMH 网关**发的，而网关会**重写**请求
> （加指纹、选流式），所以测的一直是"FMH 自己的输出"，
> **不是上游的判定**。
> 要测上游，必须**绕过网关直接打**。

`background` 参数的描述现已与官方**逐字一致**
（早期版本差 4 个字符 `use '&'` / `use the '&'`，已修正）。

### 6.2 为什么这么实现

| 决定 | 理由 |
|---|---|
| **单端口 `:8678`** | 推理面与管理面共用一个端口 —— NAS 上少开一个洞，Agent 配置也简单 |
| **Key 前缀 `fmh-`** | 一眼看出是 FMH 签发的；轮换时不会跟别的 Key 混 |
| **模型 ID 带车道前缀** | `zen/xxx` / `kilo/xxx` / `openrouter/xxx` —— 一个键贯穿清单、探测、限流账本、持久化，不用维护两套映射 |
| **指纹字面量集中在一个文件** | 上游改规格时只改一处；配回归测试锁住，防止被"顺手优化"掉 |
| **三级信任链** | 靠模型名里的 `-free` 判断免费不可靠 —— 用 `401` 探针**实测**判定 |
| **"未知 ≠ 不支持"** | 能力探测失败不等于模型不支持；把两者分开，用户才知道该不该换模型 |
| **延迟提交** | 保证上游的 429 作为**真正的** HTTP 429 返回，而不是被包成 200 |
| **"实际服务"列** | 故障转移是**静默**的。没有这一列，用户请求 A 拿到 B 的回答，会以为"这个模型今天变笨了" |
| **能力结论的来源标记** | 让用户知道每个结论有多可靠（实测 / 推断 / 未知） |

### 6.3 视觉语言

定位是**"家里的配电箱"** —— 冷静、可靠、一眼看清状态。
它常驻在 NAS 上，可能一直开着，所以**没有装饰性光效**。

色值：

| | 亮色主题 | 暗色主题 |
|---|---|---|
| 页面底色 `--bg` | `#faf7f2` 暖米白 | `#0b1220` 深蓝黑 |
| 卡片 `--surface` | `#fffdf9` | `#111a2e` |
| 侧栏 `--sidebar` | `#e8e1d1` 浅暖灰 | `#010306` 近黑 |
| 强调色 `--accent` | `#b45309` 琥珀 | `#38bdf8` 天蓝 |

界面上的车道标识用**徽章**（蓝/青绿/紫）；
故障转移靠**"实际服务"列 + `X-FMH-Model`** 变得可见。

### 6.4 FMH 独有的能力

| 补什么 | 解决什么 |
|---|---|
| **断流续写** | 上游流断了，把已产出的内容接回去并重试 —— 免密车道的流**真的会断** |
| **三级信任链** | 用 `401` 探针实测判定免费，不靠模型名猜 |
| **"未知 ≠ 不支持"** | 能力探测失败 ≠ 不支持，避免误杀 |
| **延迟提交** | 上游的 429 作为真正的 HTTP 429 返回 |
| **能力结论的来源标记** | 用户知道每个结论有多可靠 |
| **第三条免密车道（Kilo）** | 免密车道的可用性**跟着出口 IP 走** —— IP 被风控时整条车道失效。多一条免密车道就是多一个出口无关的备胎 |
| **"实际服务"列 + `X-FMH-Model`** | 把**静默**的故障转移变成可解释的 |
| **单端口 + 固定前缀 Key** | 少开一个洞，配置更简单 |
| **闸门两层错误分离** | 区分"指纹变了"（改指纹有用）和"IP 被风控"（改指纹没用，换出口才有用）—— 混淆它们会让用户"改了半天指纹，其实一直是对的" |

|---|---|---|
| Go | 16,150 行 | 5,035 行 |
| TypeScript / TSX | 4,065 行 | 828 行 |
| **合计** | **20,215 行** | **5,863 行** |

## 7. 诚实的边界

这一节很重要。

### 7.1 这是灰色地带

FMH 复现官方客户端的**线上行为**来满足免费车道的客户端限制。
这在技术上等同于"伪装成官方客户端"。

- 它**不是**绕过付费墙 —— 免费车道本身就是免费提供给官方客户端的
- 但它**确实**绕过了"只允许官方客户端使用"的限制
- 上游**可以**随时收紧，那时整个免密车道会失效

**如果你的场景有明确的合规要求，请只用 OpenRouter 车道。**

### 7.2 免费 ≠ 无限 ≠ 私有

| 误解 | 事实 |
|---|---|
| "免费 = 不限量" | ❌ 免密车道是**全局共享配额**，高峰期大面积限流 |
| "免费 = 匿名" | ❌ 你的请求会被发到上游，带你的出口 IP |
| "免费 = 稳定" | ❌ 免密车道的可用性受**IP 信誉**影响，可能整段被封 |
| "免 key = 不用 key" | ❌ 调用方仍需一把 `fmh-` Key（零成本，但不等于零凭证） |

### 7.3 数据处理

- **只记元数据** —— 模型、token 数、时间、客户端标识
- **不记提示词与回答**
- **不记请求内容**

### 7.4 上游凭据

- AES-256-GCM 加密存储
- **永不下发**给任何客户端
- 管理台**只回显指纹**（`sk-or-v1-…abcd`）
- 密钥丢失 = 已存凭据无法解密（只能重录）

### 7.5 没有做的

- ❌ 不做 HTTPS（应该放在 NAS 的反向代理后面）
- ❌ 不做 IP 白名单
- ❌ 不做多出口代理池
- ❌ 不做自动升级
- ❌ 不做 EAC 协付 / 多账号渠道

## 9. 开发与部署

### 9.1 开发

```bash
# 后端
go test ./...
go run ./cmd/fmh -addr :8678 -data ./data

# 前端（另开一个终端）
cd web && npm install && npm run dev
# → http://localhost:5173（API 代理到 :8678）
```

### 9.2 构建镜像

单个自包含的 `Dockerfile`，三个阶段：

| 阶段 | 做什么 |
|---|---|
| `node:22-alpine` | `npm ci` + `npm run build`，产出前端静态文件 |
| `golang:1.26-alpine` | `go build`，把前端 `go:embed` 进二进制 |
| `scratch` | 只放二进制 + CA 证书 + 时区数据 + passwd/group |

```bash
docker compose up -d --build
```

镜像大小约 14 MB。

### 9.2.1 发布镜像

推 `v*` tag 触发 `.github/workflows/release.yml`，自动构建
`linux/amd64` + `linux/arm64` 并推到 GHCR：

```bash
git tag v0.1.0 && git push --tags
# → ghcr.io/aBon579/free-model-house:0.1.0 / :0.1 / :latest
```

⚠️ 首次发布后要去
`https://github.com/users/aBon579/packages/container/free-model-house/settings`
把包可见性改成 **Public**，否则匿名拉取会 401。

⚠️ **运行阶段以 root 启动，但进程会自己降权** ——
   程序启动时先把 `/data` 交给 nobody（65534），然后 `setuid` 降权。
   跟 PostgreSQL / Redis 官方镜像一个路子。

   为什么不能直接 `USER 65534`：
   bind mount 的宿主目录属主是 root:root 0755，
   nobody **改不了属主**，也就**写不进去** → 首次启动失败。

⚠️ **CA 证书必须在降权之前读进内存** ——
   否则降权后读不到 `/etc/ssl/certs/ca-certificates.crt`，
   所有 HTTPS 全挂，症状是"模型清单是空的、探测全失败"。

### 9.3 环境变量

⚠️ **只有这 4 个是程序真的读的**。写了别的不会有任何效果。

| 变量 | 默认 | 说明 |
|---|---|---|
| `FMH_ADDR` | `:8678` | 监听地址。只绑本机就写 `127.0.0.1:8678` |
| `FMH_DATA` | `/data` | 数据目录。**必须持久化** |
| `FMH_SECRET_KEY` | 自动生成 | 凭据加密密钥（base64 或 hex 的 32 字节） |
| `TZ` | `Asia/Shanghai` | 时区。影响「按天」用量统计的切分点 |

> ⚠️ `FMH_SECRET_KEY` **变更后，已存的上游凭据无法解密**。
> 不设置时自动生成在 `/data/.secret-key`（0600 权限）。
> 备份 `/data` 时它必须一起备份 —— 它和 SQLite 在同一目录就是为了避免漏掉。

### 9.4 容器健康检查

```yaml
healthcheck:
  test: ["CMD", "/fmh", "healthcheck"]
```

用二进制的子命令，**不依赖 curl/wget**（scratch 镜像里都没有）。

⚠️ **列表形式的第一个元素必须是 `CMD`** ——
   Docker Compose v2（compose-go）会校验这一点，
   写成 `["/fmh", "healthcheck"]` 会报
   `healthcheck.test must start either by "CMD", "CMD-SHELL" or "NONE"`。

## 11. 已知不足

> 这一节经过**三轮**审计与修复
> （见 `docs/verification/2026-10-19-audit.md`、
> `2026-10-19-auto-probe.md`、`2026-10-19-gaps-closed.md`）。
> 三轮共抓到 **15 个真 bug**（3 个严重）。

诚实地列出来：

| 问题 | 状态 |
|---|---|
| **`go test -race` 跑不了** | ⚠️ Windows 上需要 POSIX 线程版 MinGW，本机只有 win32 线程版。已用 5 个并发测试 + `-count=20` 代替，但**不等价** |
| **合规监视器的"闸门拒绝"没在真故障下验证过** | ⚠️ 逻辑有 10 个测试覆盖，但**没法人为让上游 403** |
| **自动跨模型调用没在"免密真被 IP 封"下验证过** | ⚠️ 用假车道模拟了 `EGRESS_BLOCKED`，真实 IP 封禁没遇到过 |
| **Web UI 没有真机验证** | ⚠️ 375px 模拟器验了 DOM 布局，没有真实手机 |
| **上游变更检测只有"闸门层面"** | ⚠️ 能发现"闸门坏了"，发现不了"工具定义变了"这类**静默降级** |
| **指纹诊断只覆盖 6 个维度** | ⚠️ 上游若新增第 7 个检查项，诊断器**测不出来** —— 只能靠基线不通来发现 |
| **诊断器假设"只坏了一处"** | ⚠️ 基线不通时只能报"不止一处"，仍需人工逐项核对 |

### 11.1 第四轮已修复的（本轮）

| 严重度 | 问题 | 怎么修的 |
|---|---|---|
| 中 | `go test -race` 在 Windows 上跑不了（win32-threads MinGW 缺 POSIX 线程） | 下载 niXman POSIX-threads MinGW（`x86_64-16.2.0-release-posix-seh-ucrt-rt_v14-rev1`）→ `-race` 全绿，还抓到并修掉了一个**测试辅助函数里的真实数据竞争** |
| 中 | OpenRouter 的 `usage.cost` 没透出 | `cost_usd REAL` 列（**不能是 INTEGER** —— 小额会被截成 0）+ 按天/按模型汇总 + 界面显示 |
| 中 | 上游改了规格只能靠猜（6 轮往返） | **指纹诊断器**：单变量对照，7 次请求出结论。真实上游实测**准确定位到 UA** |
| 中 | 合规探测间隔固定 30 分钟，不能改 | 设置项 `conformanceIntervalMin`，**立即生效**（可重置定时器） |
| 低 | 探测批量固定，高峰期拿额度撞限流墙 | **自适应批量**：按上一轮限流比例缩放（100/75/50/25%） |
| 低 | 手机上 28px 的按钮点不准 | `@media (pointer: coarse)` 放大到 36/40px，**桌面端一点不改** |
| 低 | 刘海屏 / 底部横条没处理 | `env(safe-area-inset-*)` + 三个应用点 |
| 低 | 开关在手机上只有 22px 高 | 伪元素把**热区**撑到 40px，**视觉不变**（实测偏 8px 点击仍命中） |

### 11.2 已修复的（前三轮）

**第一轮（审计）**：

| 严重度 | 问题 |
|---|---|
| **严重** | 思考内容会**抢先提交响应** → 上游的 429 拿不到真正的 HTTP 状态码，延迟提交机制在最需要它的场景里失效 |
| 中 | 管理台改设置**不生效**（只写数据库，不读回运行时），要重启 |
| 中 | 「局域网推理」开关是**纯装饰** —— 关掉后推理接口照样能用 |
| 中 | 清单刷新会**清掉**模型行上的探测状态 → 前端显示"全部未知" |
| 中 | 前后端状态值不一致（`region-blocked` vs `region_block`）→ "区域限制"被显示成"未知" |
| 低 | 限流账本与探测结论**重启后不恢复** |

**第二轮（自动探测接线）**：

| 严重度 | 问题 |
|---|---|
| 中 | 异步探测用 `r.Context()` → **静默不工作**（点按钮返回 202，但一个模型都没探到） |
| 中 | 清单刷新会清掉模型行上的探测状态 → 重启后全部"未知" |
| 低 | 探测结论不写回模型行 |
| 低 | 前后端状态值不一致（连字符 vs 下划线） |
| 低 | 探测间隔/批量改了要重启才生效 |

**第三轮（补齐剩余不足）**：

| 严重度 | 问题 |
|---|---|
| **严重** | 「自动跨模型调用」的开关**形同虚设** —— 守卫写在尝试之后，**开关关了照样消耗用户自己的 OR 额度**（已修） |
| **严重** | mandatory 模型发 `enabled:false` → 上游 **400**（OpenRouter 的一部分模型完全不可用） |
| **严重** | `NormalizeEffort` 把"关掉思考"归并成 `light` → 意图在到达 lane 层之前就丢了，请求**静默失效** |
| 中 | 续写发给了**请求的**模型而不是**实际服务的**模型 → 故障转移后接不上，白费一次调用 |
| 中 | `reasoning_tokens` 全部丢失 → 客户端看不到思考占了多少 token |
| 中 | `FetchQuota` 从没被调用 → 额度栏永远空白 |
| 中 | 移动端表格被**裁断** → 375px 下 5 列完全看不见 |
| 低 | `401 Missing API key` 被当成凭据级错误 → 换模型没用，白烧一整轮候选 |

> 第一个问题的细节值得一读：延迟提交是整个设计的核心承诺
> （让上游的 429 + `Retry-After` 作为真正的 HTTP 429 返回）。
> 而"想了一分钟然后撞上配额墙"恰恰是最常见的失败形态 ——
> 所以这个 bug 恰好让机制在最需要它的时候失效。
